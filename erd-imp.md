You are correct to worry about this. When the INTERVIEWS document becomes too large, it can create performance, scalability, and concurrency problems, especially when many interviews are running simultaneously. Below is the proper way to make the system scalable.

Problems with the Current Design

The INTERVIEWS document currently stores:

interview state

bot runtime flags

job description

company info

candidate CV

evaluation

limits

conversation summary

This creates several issues:

1. Large Document Updates

MongoDB rewrites the whole document when updated. Fields like:

turn_count

phase

conversation_summary

bot_status

tts_interrupt

are updated very frequently, which is inefficient if the document is large.

2. Concurrency Issues

Multiple services may update the same document:

STT service

Agent service

TTS service

Meeting bot

This causes write contention.

3. MongoDB 16MB Document Limit

If transcripts or metadata accidentally expand inside the document, you risk hitting the 16MB limit.

Scalable Architecture (Recommended)

Split the large INTERVIEWS document into multiple collections by responsibility.

1. INTERVIEWS (Core Metadata Only)

Keep this small and mostly static.

INTERVIEWS
field	description
interview_id (PK)	UUID
candidate_name	candidate name
meeting_url	meeting link
status	in_progress / completed
started_at	start time
ended_at	end time

This document should rarely change.

2. INTERVIEW_CONTEXT (Large Static Data)

Move large text fields here.

INTERVIEW_CONTEXT
field	description
interview_id (FK)	reference
job_description	large text
company_info	large text
candidate_cv	large text

These are read once at interview start, not constantly updated.

3. INTERVIEW_STATE (Runtime State)

Move frequently updated fields here.

INTERVIEW_STATE
field	description
interview_id	FK
phase	current phase
turn_count	total turns
phase_turn_count	phase turns
conversation_summary	rolling summary
updated_at	last update

This document is small and frequently updated.

4. BOT_STATE

Runtime flags used by TTS / meeting bot.

BOT_STATE
field	description
interview_id	FK
bot_joined	chrome admitted
bot_speaking	audio playing
tts_interrupt	interrupt flag

This allows fast updates without touching other data.

5. TRANSCRIPTS (Already Good)

Keep transcripts separate (you already did this correctly).

TRANSCRIPTS

Each message becomes its own document.

This allows unlimited conversation size.

6. EVALUATIONS

Move evaluation out of INTERVIEWS.

EVALUATIONS
field	description
interview_id	FK
score	0-100
recommendation	hire / no_hire
strengths	array
weaknesses	array
summary	text

Generated once at the end.

Why This Design Scales
Small Documents

Frequent updates affect small documents only.

Parallel Services

Different services update different collections.

Example:

Service	Collection
STT	TRANSCRIPTS
Agent	TRANSCRIPTS
TTS	BOT_STATE
Meeting Bot	BOT_STATE
Agent Controller	INTERVIEW_STATE

No conflicts.

Horizontal Scaling

MongoDB can easily shard by:

interview_id

Each interview becomes independent.

This allows thousands of concurrent interviews.
