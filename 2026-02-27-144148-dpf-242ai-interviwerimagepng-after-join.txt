  ---
  Root Causes (in order of severity)

  1. Critical: Greeting fires before Chrome is in the meeting

  Main-Agent/src/main.py:131-152 — _watch_new_interviews fires the greeting
  immediately on interviews.interviews insert. TTS synthesizes and pushes audio
  to PulseAudio's virtual_mic null-sink.

  But Chrome (in meeting-bot) is still:
  - Navigating to the meeting URL
  - Waiting to be admitted by the host
  - Setting up mic/camera

  PulseAudio null-sink monitors are not a buffer — they're live streams. By the
  time Chrome is admitted and using virtual_mic_source as its mic, the audio TTS
   pushed is already gone. The candidate never hears the greeting.

  2. TTS audio failure is silently swallowed

  TTS/src/tts/main.py:101-107:

      logger.warning(f"Audio playback unavailable: {audio_exc} — synthesizing to
   DB only")

          pass
  If pacat fails for any reason (PulseAudio not yet up, virtual_mic sink not yet
   created), it logs a warning and moves on silently. The mark_played still
  runs, so audio_url gets set and TTS never retries.

  3. PulseAudio timing race

  docker-compose.yml:108-109 — tts depends on meeting-bot: condition: 
  service_started. That fires the instant entrypoint.sh starts. But
  entrypoint.sh does sleep 1 + sleep 2 before pactl load-module 
  module-null-sink. TTS might try to use pacat --sink=virtual_mic before that
  sink exists.

  4. Meeting ended with server error (image.png)

  Google Meet crashed with "video call ended because of a server error". This
  ended the session early regardless of audio issues.

   to and which sink to target. stream.write() runs in a thread-pool executor to
   avoid blocking the asyncio event loop.
